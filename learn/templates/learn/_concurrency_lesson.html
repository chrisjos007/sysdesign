Why can the result be 11?

A reads 10. B reads 10. A calculates 11. B calculates 11. A writes 11. B writes 11. The last write loses one increment. Running all three steps of A first, then B, gives 12, but one successful schedule does not prove the code is safe.

This model schedules one operation per click. A shared lock covers the entire read–calculate–write sequence. Separate server locks do not coordinate. Atomic increments represent successful database operations; waits, failures, and transaction retries are omitted.

Overlapping progress is not simultaneous execution

You produced a race while executing only one step at a time. Concurrency needs overlapping task lifetimes, not simultaneous CPU instructions. Parallelism means work actually executes at the same time.

An event loop can run another task when a task yields while waiting for I/O. A blocking call on the loop prevents that progress; async syntax does not make CPU work parallel.

Would a lock on one web server fix this?

Only if every worker touching this state uses that same lock. With a second server and a separate lock, both can still read 10. Choose “Separate locks on two servers” and repeat the alternating schedule. A database operation such as UPDATE accounts SET balance = balance + 1 WHERE id = … applies the increment at the shared storage boundary.

Protect the last seat

Two workers see one seat remaining. Both write zero and issue a ticket. The final counter is nonnegative, yet two tickets exist. What must be protected together?

Compare your reasoning

Use a conditional database update that decrements only while seats remain. Check that exactly one row changed and create the reservation in the same transaction. A failed reservation must roll back the decrement. This protects the database changes together; it does not make external payment or email effects atomic.

Even safe shared state does not make unlimited concurrency safe. If a downstream service allows 20 requests in flight, use a bounded worker pool and bounded waiting space instead of starting a task for every input. Define what happens when the limit is reached.
