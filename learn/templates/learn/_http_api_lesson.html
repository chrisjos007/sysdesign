DELETE can return 204, then 404 when repeated. The task is absent after either call: idempotence concerns intended effects, not identical responses.

What does the request key guarantee here?

In this teaching contract, a key is scoped to the authenticated caller and endpoint and retained for 24 hours. The same key and body replay the original result; a different body with that key is rejected with 409. After retention expires, the same key may create new work. These are API choices, not guarantees supplied by POST or by the header name.

What should this API promise?

201 Created describes creation. 202 Accepted does not promise successful completion. This export contract returns an operation URL after durable acceptance; status can be queued, running, succeeded, or failed. A repeat with the same request key and body returns operation 123 under the same 24-hour retention policy above.

A failed operation and an unreachable status endpoint are different outcomes. The former is a terminal result in a readable status body; the latter leaves the current state unknown. Cache behavior and permission to read an operation need their own rules.

Accept a report type and format plus a stable request key scoped to the caller and endpoint. Validate the request and authorize the caller before accepting it. Return 202 with an operation ID and status URL only after durable acceptance.

Expose queued and running as nonterminal states, and succeeded (with a result URL) and failed (with a useful error) as terminal states. Document the key and operation retention periods. In this example, the same key and body reuse one operation for 24 hours; a changed body is rejected.

A status body saying failed confirms operation failure. A network timeout during the lookup does not. ETags and If-Match protect edits to versioned resources; they do not replace request-key deduplication for creation.
