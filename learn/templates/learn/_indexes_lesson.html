Find the newest open orders

SELECT * FROM orders
WHERE tenant_id = 7 AND status = 'open'
ORDER BY created_at DESC, id DESC
LIMIT 20;

Our small dataset has 1,000 orders across 10 tenants, with 100 orders per tenant. Predict which path needs a separate sort.

Sequential scan: examine 1,000 rows, sort 10 matches, return 10 orders.

The limit bounds the answer, but this path still checks the whole table before sorting its matches.

Follow the work
  1. Read every table row.
  2. Filter for tenant 7 and open status.
  3. Sort the 10 matches.
  4. Return the 10 orders.
Check the returned order IDs

97, 87, 77, 67, 57, 47, 37, 27, 17, 7

All three paths return the same IDs in the same order. The unique ID breaks ties between equal timestamps.

Why put these columns together?

The equality filters select a tenant and status. Within that range, a backward scan of this ascending B-tree supplies created_at and id in descending order. With enough matches it can stop after 20. An index on tenant_id alone does not supply that ordering.

Logical rows or index entries examined, not disk pages, planner costs, or measured milliseconds. Index seek work, heap visibility checks, caching, and alternative plans are omitted. Choosing a path here does not force a real database to choose it.

More indexes cost storage and write maintenance. A query returning most of a table may favor a sequential scan. Validate the candidate with representative data and measured plans, including large tenants; fewer entries here is not a latency guarantee.

What should you investigate?

Check statistics freshness and data skew. These row counts describe output, not every row inspected. A cost is not milliseconds. Here actual rows is an average per loop, so multiply it by loops for total output. Matching the estimate does not remove repeated work or prove a query is fast.

EXPLAIN shows a planned strategy. EXPLAIN ANALYZE executes the statement to measure it, including writes and side-effecting functions. Use a disposable environment for experiments with effects.

An index cannot remove 51 round trips

A dashboard fetches projects, then fetches each owner separately. Assume each project has one owner and there is no application cache. Predict the query count before changing the fetching strategy.

50 projects → 51 queries.

Compare your reasoning

For 50 projects, separate lookups cost 1 + 50 = 51 queries. A join fetches projects and owners in one query. A bounded batch fetch uses two queries. An owner index may speed up each lookup, but leaves the separate round trips. Inspect query count, join keys, returned data size, and measured plans together.
